# Сравнение с эталоном `mpc-lib` (Fireblocks, MPC-BAM)

Что сравнивалось: подпись BAM (`bam_ecdsa_cosigner*.cpp`), `bam_well_formed_proof.cpp`, константы
`ZKPOK_OPTIM_*`, генерация setup на сервере. **Не читалось:** keygen клиента и сервера целиком,
add-user/redistribute, слои персистентности, тесты эталона. Эталон не собирался и не запускался,
выводы сделаны чтением кода. Эталон ссылается на версию статьи от 2025-06-01, наш код — на версию
от 6 марта 2026 (`1950.pdf`).

## Совпадает

- Структура подписи: сервер шлёт `R₂ = g^{k₂}` и `Y = X₁^{k₂}`; клиент проверяет `R₂^{x₁} = Y`, шлёт `R₁`, `R = R₂^{k₁}`,
  шифртекст и доказательство; `r = x(R + R₁^{e})` со сдвигом `e = H(X, R₁, R, m, …)`; `s = dec(S)·(k₂+e)⁻¹`.
- Сервер проверяет `R = R₁^{k₂}`, перецентрирует `dec(S)` относительно `N/2` перед переходом к mod q,
  нормализует low-s с поправкой recovery id и проверяет итоговую ECDSA-подпись.
- Setup: те же доказательства (Π_mod, Π_fac, Π_df), та же группа Π_fac `d = 2^3459 + 1169115`;
  `h, f` выводятся из идентификатора setup (то же решение круговой зависимости, что и у нас).
- Размеры: `n_a` = 1024 бит (128 Б), `n_b` = 448 бит (56 Б), ε = 192 бита (24 Б), `z₁` 152 Б, `z₂` 80 Б (у нас +1 байт знака).

## Расхождения, важные для безопасности

1. **Нулевой дайджест.** Эталон отвергает `m ≡ 0 (mod q)` (Claim 7.15 статьи) на обеих сторонах.
   У нас этой проверки не было. **Исправлено:** `sign::check_digest` в `ServerSign0::start` и `ClientSign::respond`, тест `zero_digest_is_rejected_by_both_sides`.
2. **Π_sig без DF-части в эталоне.** В эталоне доказательство содержит только `D, U, V, z₁, z₂, w₀, w₂`; нет `P̃, B̃, w₁`.
   Наша версия (по статье 2026) добавляет DF-обязательство `P̃ = s₁^a s₂^b t^µ` и связанное уравнение. Не установлено, нужна ли эта часть
   для корректности или она ужесточает доказательство относительно версии 2025; **вопрос авторам**. Если эталон отстаёт от статьи,
   это находка для Fireblocks, а не для нас.
3. **Диапазон λ₀.** Эталон: `n_λ0 = max(n_a + 2ℓ + ν, n_b + n_λ + ε) + ν` = 1408 бит (176 Б), ответ `w₂` 200 Б.
   У нас: `n_λ + ε + n_b + ν` = 1024 бит, `w₂` 153 Б. Разные версии статьи; сверить с текстом статьи и с авторами.

## Расхождения по функциональности (эталон шире)

- Нет **HD-деривации** (BIP32): эталон сдвигает долю на `delta` и использует производный открытый ключ в `Y` и в `e`.
- Нет **пакетной подписи** нескольких блоков за вызов (`MAX_BLOCKS_TO_SIGN`), нет режима `POSITIVE_R` (нужен для Stark и подобных).
- Только secp256k1; эталон поддерживает secp256r1 и Stark.
- Нет **add-user / redistribute** (смена состава участников).
- **Состояние сервера между раундами.** Эталон хранит `k₂` через интерфейс персистентности с `load_signature_data_and_delete`
  (одноразовость). У нас состояние `ServerSign1` живёт в памяти и не сериализуется, поэтому сервер без сессионной
  привязки (несколько процессов за балансировщиком) пока не построить. Это нужно решать до интеграции.
- Эталон — C++/OpenSSL; у нас чистый Rust без нативных зависимостей.

## Различия в реализации

- Nonce: эталон берёт случайный `k` из генератора, мы — hedged (хеш свежей случайности, секрета и контекста).
- Проверка Π_sig у эталона идёт **с приватным ключом Paillier** (`commit_with_private`, вычисления mod p² и mod q²), у нас — по открытому.
  Это возможный выигрыш скорости на шаге S3 (сейчас 38 мс при бюджете 40). Применимо только потому, что проверяет владелец ключа.
- Привязка к сессии: у эталона AAD из `key_id`, `server_id`, `client_id`, `tx_id`; у нас `ssid` (хеш setup, id сторон, `key_id`, дайджест, `R₂`).
- Эталон проверяет `gcd(S, N) = 1`; у нас `check_ciphertext` проверяет `S ∈ Z*_{N²}`.
